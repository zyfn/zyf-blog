## 先给结论

多 Agent 的价值来自**职责隔离和并行证据**，不是“同时打开更多模型”。如果任务仍能由一个上下文清晰、验证明确的 Agent 完成，就不要先增加协调层。

一个可靠的升级顺序是：

> 单 Agent → Subagent → 独立 Session / Worktree → Agent Team → Scripted Workflow

只有前一层出现了可观测瓶颈，才进入下一层。

## 五种机制分别解决什么

| 机制 | 核心价值 | 适合 | 主要代价 |
|---|---|---|---|
| 单 Agent | 上下文集中，沟通成本最低 | 边界清楚、一个模块内的任务 | 调查噪声可能挤占主上下文 |
| Subagent | 隔离调查、日志和专业角色 | 调用链、安全、测试覆盖分析 | 需要设计清楚的返回格式 |
| 独立 Session + Worktree | 隔离完整任务和文件状态 | 多个互不依赖的实现 | 最后仍要人工或集成 Agent 合并 |
| Agent Team | 成员能互相沟通和挑战 | 竞争假设、跨角色协作 | Token、协调与一致性成本更高 |
| Scripted Workflow | 可读、可重跑的大规模扇出 | 数十至数百个同类工作项 | 必须设计停止条件、并发与失败处理 |

## 一个简单的选择算法

先问四个问题：

1. **任务之间是否真的独立？** 如果不能各自验收，就先不要并行。
2. **成员是否需要互相沟通？** 只需向主 Agent 汇报时，Subagent 已足够。
3. **是否会并行写代码？** 会写就先解决 Worktree 和文件所有权。
4. **流程是否需要重跑？** 需要稳定复现时，把编排写成 Workflow，而不是依赖临场对话。

## 委派合同必须写清六件事

每个 Worker 至少要得到：

- 唯一目标；
- 明确的读写范围；
- 输入与依赖；
- 可执行验收；
- 结果返回格式；
- 必须停止并请求决策的条件。

例如，“检查支付模块有没有问题”无法验收；“追踪取消事件到退款落库的调用链，返回已证实路径、竞争假设和缺失测试，不修改文件”才是一份可执行委派。

## 三个常见失败模式

### 多个 Agent 做同一份泛化 Review

这通常只会生成几份相似意见。更好的拆法是：正确性、安全、并发和测试充分性各自负责一类证据。

### 多个 Agent 共享同一工作目录

并行写入会把协作问题变成文件竞争。使用独立 Worktree，并明确每个 Worker 的文件所有权。

### 用“Turn 结束”判断业务完成

一个 Agent 停止输出，只代表本轮执行结束。业务完成必须由明确结果、验收命令和交付状态共同证明。

## 推荐落地方式

先挑一个真实但低风险的跨模块任务：让两个 Subagent 分别调查调用链和测试缺口，主 Agent 负责计划与集成。记录上下文节省、重复工作、合并冲突和验证时间。只有数据表明单层委派不够，再尝试 Team 或 Workflow。
