2026 年 8 月 13 日，一个名为 DeepSeek Harness 的项目登上 Hacker News 首页，拿到七百多个赞。但高赞评论里最醒目的一条是个疑问："所以这到底是什么？它居然能上第一，有点奇怪。README 除了安装说明几乎什么都没有。"（[Hacker News 讨论](https://news.ycombinator.com/item?id=49285244)）

这个困惑不丢人，它点中了盲区：DeepSeek 这次发布的不是一个能立刻上手的聊天产品，也不是一个新模型，而是一层大多数人从没听说过的东西——harness，把模型变成智能体的运行系统。官方发布页只用几行字介绍它，把其余一切指向了代码仓库。

为了弄清楚它到底是什么，我做了三件事：把官方架构文档、插件教程和 Cordis 教程完整读了一遍；读了支撑整个设计的[论文](https://arxiv.org/abs/2608.25512)；然后在本地把它装起来跑了一遍，把真实的运行配置抓了出来。本文就是这次拆解的结果。

<Callout title="版本边界">
本文基于 2026-09-01 的 [GitHub 仓库](https://github.com/deepseek-ai/deepseek-harness)与[官方发布页](https://www.deepseek.com/harness/en/)，本地实跑版本为 npm 包 `@deepseek-ai/dsh` 0.1.1-rc.2。项目自称开发者预览（developer preview），README 用大写字母警告"未来将出现破坏兼容性的变更"，文中机制可能随版本变化。
</Callout>

## 模型是灵魂，Harness 是身体

先说清楚 harness 是什么。大模型本身只做一件事：接收一段文本，返回一段文本。它可能在回复里说"我需要调用一个工具"，但它自己不能真的去执行——不能读文件、不能跑命令、不记得两步之前发生了什么，更不知道哪些操作应该先问你一声。

这些模型之外的活，都由一层运行系统完成：组装上下文、暴露工具、执行命令、施加权限、保存状态、再把结果带回下一次模型调用。这层系统就是 harness。DeepSeek 官方发布页给出的公式是 "Agent = Model + Harness"，并解释说"模型是智能体的灵魂，harness 让智能体理解环境、使用工具，并在真实环境中持续工作"。

一个类比：模型像一位只会做决策的司机，harness 是整辆车——引擎、传动、刹车和行车记录仪。同一位司机开不同的车，能到达的地方完全不同；车决定了意图能变成什么。我们熟悉的 Claude Code、Codex CLI、OpenCode，本质上都是各自模型外面的车（本博客对 Codex 那辆车的内部构造有一篇完整拆解：[在意图与行动之间：Codex Harness 如何工作](/posts/codex-agent-runtime)）。

由此得到一个判断：AI 助手的能力上限不再只由模型决定，harness 决定模型的"聪明"能兑现成多少行动。这正是各家实验室开始认真对待这一层的原因，也是理解这次发布的起点。

## 一份配置文件就是一个 Agent

市面上的 harness 大多是成品：你可以往上加工具、加插件，但骨架——执行循环、会话管理、权限系统——封死在代码里，看不见也动不了。DeepSeek 的 Harness（命令行工具叫 `dsh`）把骨架也做成了数据。

我在本地装好 0.1.1-rc.2 后，运行了一条官方文档建议的命令：

```bash
dsh --profile web --dump-config
```

它打印出这次启动实际装配出来的完整插件树——503 行 YAML。节选如下（包括行首的层标注，这是输出原样）：

```yaml
# == @deepseek-ai/dsh-base
- id: timer
  name: '@deepseek-ai/cordis-plugin-timer'
- id: llm
  name: '@deepseek-ai/dsh-llm'
- id: session
  name: '@deepseek-ai/dsh-session'
- id: agent-default-model
  name: '@deepseek-ai/dsh-agent-default-model'
  config:
    provider: deepseek-official
    model: deepseek-v4-flash
# == @deepseek-ai/dsh-base, patched by @deepseek-ai/dsh-web-app
- id: sandbox-policy
  name: '@deepseek-ai/dsh-sandbox-policy'
  config:
    mode: workspace-write
# ……共 503 行，界面、工具、权限、遥测全在其中
```

这份输出值得逐层看。所谓"一切皆插件"在这里不是口号，是可以逐行数出来的事实：

- **默认模型是一行配置**。`deepseek-v4-flash`，来自 `deepseek-official` 提供方。想换成任何 OpenAI 兼容端点，改这一行。
- **权限体系是三档预设**：`read-only`、`workspace-write`、`danger-full-access`，默认 `workspace-write`；审批策略默认是"问"，只有显式选了全权限档才会变成"从不问"。
- **界面本身是三十多个 `ui-*` 插件**：主题、布局、侧边栏、对话视图、工具卡片、子 Agent 面板、轨迹视图……你看到的 Web 界面，和模型适配器一样，也是树上可替换的一行。
- **连"计划模式"的提示词都是配置**。`plan-mode` 这一行的 `config.section` 字段里，放着一整段告诉模型"你现在处于计划模式、先探索再提交计划"的系统提示。产品文案即配置数据。

组装规则在[架构文档](https://github.com/deepseek-ai/deepseek-harness/blob/main/docs/architecture.md)里写得很清楚：一次运行的 `dsh` 是一棵按顺序叠加的插件树，配方（profile）列出它叠哪些套件（bundle），每层补丁（patch）按 `id` 定位一行并整行替换配置，后写的赢。官方出厂五个配方：带浏览器界面的 `web`、一次性执行的 `headless`、供程序调用的 `sdk` 系列、面向自动化协议的 `acp`。日常启动只需一条命令：

```bash
npx @deepseek-ai/dsh web
```

本地起一个 Web 界面（默认 `http://127.0.0.1:3080`），填入 DeepSeek API key、选定工作目录，就能让 agent 读写文件、执行命令、拆解任务。到这一步，它用起来和其他编程助手没有区别。

区别在于树的深处。有一个细节是我这次运行才注意到的：配置行的排列顺序没有加载语义，某个插件何时激活，由它声明依赖的服务是否就绪决定。换句话说，这棵树不是按顺序执行的脚本，而是一张按依赖关系自行点亮的网络。这句话的分量，读完论文那节会更清楚。

那么"插件"本身是什么？官方[插件教程](https://github.com/deepseek-ai/deepseek-harness/blob/main/docs/user/develop/basic/index.md)给的最小形态是一个导出 `apply` 函数的 TypeScript 模块：

```ts
import type { Context } from '@deepseek-ai/cordis'

export const name = 'hello-plugin'

export function apply(ctx: Context) {
  console.log('[hello-plugin] plugin loaded!')
}
```

框架加载插件时调用 `apply`，传入一个共享的 `ctx` 上下文对象，插件通过它注册能力。整个项目的扩展方式就这一个入口：往 `ctx` 上挂。

## 每个零件都有撤销键

任何做过插件系统的人都知道，真正的难题不是"能不能插上"，而是：运行到一半把零件拆下来，它留下的注册、订阅和副作用怎么办？一个工具注册了、一个事件监听挂上了、一段提示词注入了，如果卸载时清不干净，系统会越用越脏，"热插拔"就永远只是演示。

DeepSeek 的答案写在它底层的插件框架 [Cordis](https://github.com/cordiverse/cordis) 里：**一切注册都是可逆的效果（revertible effect）**。教程里的例子很直白——插件起了一个定时器：

```ts
export function apply(ctx: Context) {
  ctx.effect(() => {
    const timer = setInterval(() => console.log('tick'), 200)
    return () => clearInterval(timer) // 卸载时自动执行
  })
}
```

`ctx.effect()` 里放获取资源的代码，返回释放它的函数；插件卸载时，运行时替你调用释放。更关键的是，大多数时候你根本不需要手写这一层：`ctx.on()` 挂的事件监听、通过 `ctx.tools.register()` 注册的工具，本身就已经是效果——监听器随插件卸载自动消失，没有人需要手动记账。

每个加载中的插件实例在运行时有一个状态机：

```text
PENDING → LOADING → ACTIVE → UNLOADING → DISPOSED
              ↘ FAILED
```

卸载不是把对象扔掉，而是沿状态机走完 `UNLOADING`：所有清理函数按注册的逆序执行（异步清理并发进行），递归卸载它挂载的子插件，全部完成后才到 `DISPOSED`。

这套机制有正式的学术表述。支撑 Cordis 的论文 [_A Programming Paradigm for Spatiotemporal Composability_](https://arxiv.org/abs/2608.25512)（北京大学与 DeepSeek 合作，2026 年 8 月发布于 arXiv，cs.PL 方向）把上面的设计命名为**时间可组合性**（temporal composability）：组件被移除时，其副作用能够被完整撤销。论文的做法是把经典的"效果"概念提升为运行时机制——每一次上下文变换都携带一个逆操作，由运行时统一持有；于是撤销不再依赖组件作者的自觉，而是系统的结构性保证。

论文摘要的第一句话也值得抄下来，它直接点明了动机："现代软件——从插件系统到自我演化的智能体 harness——越来越需要动态组合，但其形式化基础仍然发育不足。"一家模型实验室为插件的热插拔写一篇编程语言方向的论文，这件事本身就在说明它把 harness 当成了什么：不是产品，是需要形式化基础的系统问题。

一位读完论文的 Hacker News 用户给出了第三方评价："它给插件系统加上了热重载和动态启用/卸载能力……他们把它推得更远，一直推到 UI 组件。"这是社区视角的判断，不是官方承诺；但和我在配置树里看到的三十多个 `ui-*` 插件对得上。

## 零件自己决定何时上线

时间维度解决"拆得干净"，空间维度解决"装得起来"。插件树动辄几百行，谁依赖谁？传统做法是手工编排启动顺序，而手工编排的顺序一定会在某个夜晚骗你。

Cordis 的做法是：插件用 `inject` 声明需要的服务，运行时等所有依赖就绪才加载它。需要 `tools` 服务的插件，在 `ctx.tools` 存在之前停在状态机的 `PENDING` 格子里；哪个服务先上线，依赖它的插件就先点亮。这就是论文说的**空间可组合性**（spatial composability），机制名叫"响应式余效果"（reactive coeffect）：上下文的每一次变化，都会对照每个组件声明的需求分类，驱动它的激活与去激活。我在上一节末尾注意到的"行序没有加载语义"，正是这条机制在配置层的投影。

组件之间的通信则用类型化事件。事件的调度模式是契约的一部分，共五种：广播观察（`emit`）、层层包裹的中间件（`waterfall`）、并行（`parallel`）、顺序取首个有效值（`serial`）、一票否决（`bail`）。其中 `waterfall` 是拦截能力的来源：每个监听者拿到参数和一个 `next()` 延续，可以改写传递下去的内容，也可以不调用 `next()` 直接否决整条链。

这套抽象落到 harness 上，就是处处可插拔的拦截点。架构文档里最重要的两条规则：

- `agent/pre-step` 是瀑布事件，**决定模型能看到什么**。监听者可以改写即将进入模型的消息，也可以整体否决；被否决的输入仍会关闭一个持久化的 turn，日志里留下这次尝试的记录。
- 扩展插件只依赖 `agent` 接口，**永远不直接依赖 `agent-loop`**——文档原话是"这样循环本身保持可换"。也就是说，智能体的执行循环是一个默认实现，不是唯一的实现。

再接上能力接缝（seam）：一个能力由接口定义、实现方、消费方三个角色组成，换掉实现方，整组能力跟着迁移。文档举的例子是把文件系统和子进程的实现指向远程沙箱，Bash、终端和 LSP 会一起搬过去，不需要为每个工具单独改造。配置树里 `sandbox`、`subprocess`、`subagent` 各自独立成行，就是为这种整体替换预留的位置。

论文给这一层补上了最后一块理论：它证明在上述机制下，不同组件的效果可以交错执行而互不干扰（论文称之为观测等价之上的组合演算），并把可组合性从单个组件推广到整个交错运行的系统。通俗地说：它想证明"几百个插件同时热插拔"这件事在原理上不会互相踩脏。至于证明与工程实现之间还有多远，没有人验证过，包括我。

## 从一句话到一条命令之间

理解了骨架，再看一次真实的工具调用要穿过什么。官方[工具执行管线](https://github.com/deepseek-ai/deepseek-harness/blob/main/docs/tool-execution-pipeline.md)把这条路径画成了流程图，整理出来是这样：

```text
模型回复中出现工具调用
  → tool/call 先记入日志（参数是模型产出的原始 JSON）
  → tools/pre-execute 瀑布：hooks、权限、沙箱策略依次过手
  → 单调守卫：只能否决或弃权，身份受保护
  → 审批提示：无人应答或答不了，按否决处理
  → tools/execute 瀑布：超时、重试、指标包裹真正的执行
  → 工具本体执行（写文件先过 fs/* 意图闸门）
  → tools/post-execute 瀑布：放行、阻断、替换结果或追加上下文
  → 最终结果冻结为不可变记录 → tool/result 记入日志
```

几个设计选择值得普通读者留意。第一，**先记账后执行**：`tool/call` 事件在工具真正运行之前就写进日志，记录的是模型产出的原始参数，不经过任何美化。第二，**审批失败按否决处理**，而不是按放行——审批服务缺席或无法应答时，默认是拒绝，这个方向选对了安全的那一边。第三，权限、钩子、沙箱都不写死在循环里，而是挂在三个瀑布事件上；换一个权限方案，是挂一个新的监听者，不是改执行循环。

这条管线发生在一个叫 turn 的结构里：一个 step 是一次模型请求加上它调用的工具，一个 turn 是零个或多个 step。用户的一句话进来，循环开始认领输入、组装上下文、请求模型、执行工具，直到没有欠下的动作为止。你中途插话，新消息进入同一个 turn 的收件箱；你反悔，取消会留下 `interrupted` 标记。

## 模型看到的一切都有账本

对普通使用者来说，AI 助手最让人不安的问题之一是：它到底看了什么、做了什么。Harness 把可追溯做成了架构级的承诺。

官方发布页写道："每一次运行都可追溯。模型看到的一切都被记录在只追加（append-only）的会话日志里。"[会话子系统的文档](https://github.com/deepseek-ai/deepseek-harness/blob/main/docs/subsystems/session.md)把这句话收紧成一条硬性不变量：**"模型可见即已记录"**（Model-visible means logged）——任何能进入模型请求的内容，必须能从会话日志重建出来，运行时还有断言持续校验这一点。

日志的事件词汇表本身就是设计的一部分：

| 事件 | 记录什么 |
| --- | --- |
| `turn/start` / `turn/end` | 轮次的打开与结束原因 |
| `step/start` / `step/end` | 一次模型请求和它的工具 |
| `user/message` | 进入模型的输入及其来源（人、注入的上下文、目标续轮） |
| `assistant/chunk` | 原始流式块，保留到 token 级 |
| `assistant/message` | 组装后的回复、token 用量、中断标记 |
| `tool/call` / `tool/result` | 模型发出的原始调用参数与最终结果 |

注意两件事。模型的对话历史**不从别处存取，而是从这条日志推导出来**——回放就是重新推导，恢复和分叉也基于同一条事件流，所以不存在"历史文件"和"日志"对不上的问题。同时 `assistant/chunk` 把流式输出的原始块也留在日志里，这意味着回放可以精确到逐 token 重建当时的界面。

我在本地配置树里也看到了这套机制的落盘形态：`session-persistence-jsonl` 把会话写成主目录下的 JSONL 文件，`session-query-sqlite` 维护查询索引，`session-projection` 负责把事件折叠成客户端视图，遥测默认关闭、可指向自建端点。日志、索引、投影三层各司其职——这几乎是把"事件溯源"教科书写进了出厂配置。

这条约束的含金量在于它排除了暗角：不存在"模型看到了但日志里没有"的输入。提示词注入、工具结果、中途塞进来的上下文，凡是影响过模型决策的东西都有账可查。将来评估任何 AI 助手，都可以拿这句"模型可见即已记录"当标尺问一问。

## 实验室们真正在争什么

把视角拉远一点。Harness 发布之前，编程助手形态的 agent 已经竞争了一年多。Hacker News 上有一条被反复引用的评论："到此为止，最后一家发布了值得用来写代码的模型、却没有自家 harness 的实验室，也交卷了。"

这句话点破了格局：模型厂商几乎都在补齐自己的 harness，因为模型与 harness 协同得越好，产品的兑现能力越强。但 DeepSeek 的选择和这条常规路径不太一样。官方把 Harness 定位为"面向全世界 agent harness 开发者的开发者预览"——它不是 DeepSeek 模型的专属驾驶舱，而是一个任何人都可以拿来组装自己 agent 的开放运行时。配置树本身就是证据：默认模型只是其中一行，`llm` 服务是个接缝，换掉它不需要碰任何源码。与此同时，官方维护的 [awesome-deepseek-agent](https://github.com/deepseek-ai/awesome-deepseek-agent) 列表显示，DeepSeek 的模型已经被接入了二十多个第三方工具，从 Claude Code、Codex 到各种开源终端助手。

这两件事放在一起，可以读出一种策略——需要声明，这是我的推断而非官方表态：DeepSeek 延续了它"把重资产开源"的一贯动作，只是这次开源的不是模型权重，而是"组装智能体的权利"。如果开发者基于 Cordis 和 `dsh` 长出自己的 harness，DeepSeek 的模型就自然地坐在这个生态的中心。发布约 19 天，仓库收获超过 20 万 star、2.3 万 fork（2026-09-01 观察），说明注意力已经到位。

社区也有冷静的质疑。有用户在 HN 上问：第一方 harness 搭配自家模型，真的有优势吗？目前没有任何公开证据表明 DeepSeek 的模型为 Harness 做过协同训练，这个问题仍然是开放的。

## 这个预览版还不能承诺什么

注意力不等于成熟度。在决定认真对待它之前，有三条边界必须看清。

它会变。开发者预览阶段，官方明确预告破坏兼容性的变更；我实跑的包版本叫 `0.1.1-rc.2`，仓库里的基础套件是 `0.1.2-alpha.3`，版本号本身就说明了一切。今天写的插件和配置，明天可能需要重写。

它没有被安全审计过。项目自带的[安全说明](https://github.com/deepseek-ai/deepseek-harness/blob/main/SAFETY.md)写得很直白：它能执行模型生成的代码和命令、加载第三方插件、访问网络和凭证，"不能被视为安全的或可上生产的"；沙箱与审批能降低风险，但不保证隔离。官方的建议是最小权限、一次性虚拟机或容器、先备份、审查每一个插件和命令。我在配置树里看到的那档权限预设名叫 `danger-full-access`——连命名都在提醒你它存在。

范式不等于体验。"一切皆插件"解决的是架构的可换性，不直接回答"用起来顺不顺"。503 行的配置树对设计者是自由，对新手是墙；README 的简陋和概念的密度，都还在消耗社区的好感。一位 HN 用户读完论文后的评价很典型："可能有用，但没有那么有用。"它真正的价值要等生态来验证。

回到开头那个问题："这到底是什么？"现在可以给一个完整的答案：它是 DeepSeek 对下一层竞争的下注——agent 的未来不该只有一个又一个封闭成品，还应该有一套谁都能拼装、每个零件都可替换、每笔账都可追溯的公共运行时。他们用一篇论文给"可替换"打底，用一份 503 行的配置树给"一切皆插件"举证。

这个判断成立与否，取决于一个可以观察的条件：接下来几个月，`dsh-plugin` 话题下能不能长出真实繁荣的插件生态。如果只有 star 没有插件，它就只是一次漂亮的工程实验；如果生态长出来了，8 月 13 日这一天可能会被记住——不是因为又一个 AI 产品发布，而是因为 AI 助手的"身体"第一次成了可以逐行检阅的公共基础设施。
