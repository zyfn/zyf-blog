## 不是每条好 Prompt 都值得做成 Skill

Prompt 解决一次沟通；Skill 解决一类可重复工作。只有同时满足以下条件时，才值得资产化：

- 流程会重复出现；
- 输入和完成标准可以描述；
- 方法包含模型无法每次稳定猜到的知识；
- 有脚本、模板或参考资料可以复用；
- 错误执行的代价值得通过规则降低。

一次性的需求澄清、临时探索和高度依赖当前对话的判断，留在 Prompt 中通常更合适。

## 一个 Skill 应回答五个问题

1. **什么时候触发？** 描述必须让 Agent 能判断适用场景。
2. **需要什么输入？** 文件、参数、系统状态和用户选择要明确。
3. **按什么顺序做？** 只写真正影响结果的步骤。
4. **可以调用什么？** 工具、脚本和权限尽量收窄。
5. **怎样算完成？** 给出命令、文件、结构或外部状态的验收。

## 推荐目录结构

```text
release-check/
├── SKILL.md
├── scripts/
│   └── collect-release-evidence.sh
├── references/
│   └── release-policy.md
└── templates/
    └── release-report.md
```

`SKILL.md` 负责路由和方法；脚本负责确定性动作；Reference 负责较长知识；Template 负责稳定交付格式。不要把所有内容重新塞回入口文件。

## Skill、Hook 与 MCP 怎样分工

| 机制 | 负责什么 | 例子 |
|---|---|---|
| Skill | 教 Agent 怎样完成一类工作 | 数据库迁移审查方法 |
| Hook | 某事件发生时必须执行的确定性检查 | 提交前运行迁移校验 |
| MCP | 提供外部工具和实时数据 | 读取 Schema、慢查询和变更记录 |
| Plugin | 将以上能力版本化分发 | 安装一整套数据库助手 |

一个成熟的数据库变更助手，通常是 Skill 规定分析步骤，MCP 提供实时 Schema，Hook 在执行前检查环境和审批票。

## 从现有 Prompt 迁移的步骤

### 第一步：找出稳定部分

把当前任务特有的信息删掉，只保留多次任务都成立的方法、边界和验收。

### 第二步：把事实和流程分开

稳定流程写进 `SKILL.md`；大段领域资料放进 Reference；可机械执行的部分变成脚本。

### 第三步：设计失败路径

明确缺少输入、权限不足、外部系统不可用和验收失败时怎么停止。好的 Skill 不只描述成功路径。

### 第四步：用真实任务验证

至少在三个差异明显的任务上运行。观察误触发、漏触发、重复读取和工具权限是否过宽，再决定是否给团队分发。

## 维护原则

Skill 是代码资产，不是静态提示词收藏夹。它需要负责人、版本、变更说明、最小测试样例和废弃策略。只有这样，Agent 的“经验”才能真正进入工程系统，而不是换一种形式继续漂移。
