## 为什么必须拆成三层

Agent 安全配置最常见的误区，是把所有开关理解为一个从“保守”到“自动”的滑杆。实际上，它们回答三个不同问题：

| 控制层 | 回答的问题 | 典型机制 |
|---|---|---|
| Permission / Policy | Agent 是否应该尝试这个动作 | Allow、Ask、Deny、Managed policy |
| Approval | 这个具体动作是否必须先由人确认 | On request、交互审批、单次重试 |
| Sandbox | 即使动作被尝试，它在技术上能访问什么 | 文件根、网络、进程、容器、VM |

只配置其中一层，往往会留下错误安全感。

## Permission 是决策边界

Permission 适合表达“哪些工具和命令属于正常工作”。例如：

- 允许读取仓库和运行单元测试；
- 推送、发布和生产写入必须询问；
- 永远拒绝读取 `.env`、Secret 目录或越过项目边界。

对绝不能发生的动作，使用确定性的 Deny 或组织策略，不要只在 Prompt 里写“请不要”。

## Approval 是人类闸门

Approval 解决的是某一次具体动作。它适合：

- 安装依赖；
- 首次访问外网；
- 写外部工单或评论；
- 推送分支、创建发布、修改云资源。

批准一次重试，不等于永久放宽同类动作。反过来，无人值守 CI 也不能等待人工审批，因此必须提前定义更窄的 Allowlist。

## Sandbox 是最后的技术边界

Sandbox 应假设 Agent 可能犯错，也可能读取到恶意指令。它通过操作系统或容器限制文件、网络与子进程。

需要注意：Shell 被沙箱限制，不代表 MCP、Browser、Computer Use 和其他外部工具自动受到同一边界。每类工具都要单独评估。

## 四种典型基线

### 陌生仓库调查

只读、无外网、禁止凭证访问。先理解项目，再决定是否信任项目 Hook、脚本和扩展。

### 日常本地开发

允许当前 Worktree 写入和常见测试命令；网络按需；推送、数据库和外部消息保留询问。

### 自动化 Review

只读仓库、固定输入输出、无生产凭证。发现问题可以生成报告或补丁，但不直接合并。

### 无人值守修复

运行在短生命周期容器或 VM 中，使用短期最小权限凭证；限制网络出口、预算、时间和可修改目录；交付 PR 而不是直接发布。

## 最后用一个问题检查配置

假设 Agent 误解了任务，并且刚刚读取了一段恶意网页内容：它现在能读取什么、能写什么、能把数据发到哪里、哪个动作仍需要人确认？如果答案不清楚，安全边界就还没有设计完成。
