# 技术博客写作指南

这份文档是本博客长期使用的写作与审稿标准，适用于人工写作以及与 Agent 协作写作。

博客是发布载体，不是单一文体。实操教程、源码解读、系统 Deep Dive、判断型白皮书、案例复盘和参考手册都可以发布在这里；不按篇幅或标题数量机械判断质量。共同目标是让读者获得一种可以迁移的理解、判断或行动能力，而不是只记住一组名词。

这份指南以可执行写作流程为主。关于“辞达”“文质”“风骨”、文本无法回答追问以及写作过程具有递归性等思想来源，见[《写作哲学原典研究：从思想生成到读者重建》](./writing-philosophy-sources.md)。原典研究提供观察视角，不替代事实、证据和具体写作判断。

## 使用方式

每次写作按以下顺序执行：

1. 建立写作契约；
2. 选择文章类型和主导关系；
3. 只写承重句，确认主线成立；
4. 收集与标注证据；
5. 扩写正文、代码和图表；
6. 分轮修订；
7. 通过发布质量门。

不要要求第一稿同时完成发现、论证、表达和压缩。证据可以迫使命题缩小，结尾也可以迫使开头重写。

## 写作前先建立契约

起草前先在草稿或工作记录中回答以下问题，答案不直接发布到正文：

```text
文章类型：教程 / 系统解读 / 白皮书 / 案例复盘 / 参考手册
目标读者：谁具备哪些前置知识
读者起点：他现在困惑、误判或做不到什么
读者终点：读完后能解释、判断或完成什么
中心句：全文唯一不可删除、可以被质疑的判断
主导关系：解释 / 论证 / 指导 / 分析 / 复盘
成立边界：哪些条件变化后，中心句需要缩小或失效
证据基线：官方资料、源码版本、运行环境、样本和校验日期
```

- 中心句要比主题具体，比口号可质疑，比摘要更有方向。
- 如果读者、中心句或文章类型仍不清楚，先调查和列承重句，不用流畅文字掩盖空白。
- 文章可以同时解释原理并给出建议，但只能有一个主任务；其他内容必须服务于主任务。

## 按文章类型选择结构

| 类型 | 主任务 | 推荐认知路径 |
|---|---|---|
| 实操教程 | 让读者完成一项操作 | 可见结果 → 前提 → 最小路径 → 请求与响应 → 验证 → 常见失败 → 生产边界 |
| 系统或源码解读 | 让读者重建运行模型 | 真实困惑 → 最小模型 → 关键部分 → 一次完整流动 → 状态与故障 → 版本边界 |
| 判断型白皮书 | 让读者形成工程选择 | 真实问题 → 中心判断 → 最小模型 → 核心维度与证据 → 场景 → 最强异议 → 采用边界 → 附录 |
| 案例复盘 | 让读者理解问题如何发生 | 可观察现象 → 竞争解释 → 区分证据 → 根因 → 选择与结果 → 尚未解决处 |
| 参考手册 | 让读者准确查询 | 适用版本 → 使用入口 → 精确映射 → 代表示例 → 差异与异常 → 更新方法 |

- 白皮书可以很长，也可以带完整附录；正文负责建立判断，附录负责查询，不能让资料清单淹没主论证。
- 教程可以解释原理，Deep Dive 可以给实践建议，但不要让一篇文章同时争夺教程、百科、新闻和观点评论四个中心。
- 文章类型不需要新增公开栏目；标题、摘要、开头和章节结构应让读者自然识别。

## 用承重句搭骨架

扩写前先单独写出：开头的真实问题、全文中心句、每个主章节唯一的承重句、结尾新增的判断。

- 这些句子单独排列后必须形成完整路径；如果顺序可以随意交换，说明关系还没有建立。
- 每个主章节只承担一种主要动作：提出、解释、证明、比较、限定、反驳或指导。
- 删除某个章节后若理解不变，应合并或删除；不要因材料已经收集就强行保留。
- 普通长文常见 4–7 个主章节；白皮书、Deep Dive 和参考手册可以更多，但每个主章节必须不可替代，查询型内容优先收束到附录。

## 开头、正文与结尾

### 开头

- 尽快进入一个真实问题、可观察现象、任务或张力；不从宽泛时代背景、产品口号和功能菜单开始。
- 在较短篇幅内给出读者为何需要继续读、文章中心判断和必要版本边界。
- 不连续发布“导读”“执行摘要”和重复摘要。
- 自造场景必须明确为假设，不制造仿佛真实发生的时间、人物、数字或后果。

### 正文

- 页面标题是唯一 H1，正文从 H2 开始；H3/H4 只能属于前面的章节。
- 标题直接表达主题，不使用“一、”“二、”“1.”“2.1”等人工序号。
- 不使用 `---`、`***` 或 `<hr>` 分割章节；层级通过标题、段落动作、节奏和留白建立。
- 一个段落只完成一个主要动作。事实、推断、判断和建议不要压进同一个超长句；重要转折与边界单独成句。
- 每个专业细节都要服务于中心问题；只增加完整感、不改变理解的材料应删除或放入附录。

### 结尾

- 新增采用条件、行动方向、尚未解决的问题或可以迁移的判断。
- 不换词重复摘要，不强行升华，也不替读者宣布唯一结论。
- 给继续讨论留下接口：什么情况会改变结论，下一步应该验证什么。

## 证据与认识论边界

重要陈述要能区分为：

- **已验证事实**：官方文档、源码、Schema、命令输出、测试或真实运行明确支持；
- **基于资料的推断**：由多个事实推得，说明推理桥梁和不确定性；
- **个人工程判断**：明确是选择标准、经验或价值取舍，不借官方链接假装成产品事实；
- **行动建议**：说明适用条件、成本和失败方式，不把一个成功案例写成普遍规律。

写作要求：

- 版本敏感的事实写明产品或源码版本、校验日期和 Surface。
- 优先使用官方文档、源码、标准、论文和原始数据；二手资料只用于发现线索或补充观点。
- 说明证据如何支持结论，不把链接排列在判断旁边就当作论证完成。
- 无法确认时缩小结论或保留未知，不用肯定语气补洞。
- 不虚构真实用户、事故、数据、引语、运行结果或作者经历。
- 不公开凭证、员工信息、私有域名、本机绝对路径、内部交接、未公开规划或未经验证的产品结论。

## 代码、图表与表格

- 代码只保留证明关键行为的部分，并告诉读者应该观察什么。
- 核心示例必须可运行，或明确标注为简化伪代码。
- 教程示例同时给出请求与响应；涉及事件流时，再给出关键通知顺序、最终状态和验证方法。
- 架构图用于边界、层级和依赖；流程图用于顺序、状态和分支；图后解释它澄清了什么。
- 表格只用于精确映射、比较和查询。单元格开始承载论证时，改回段落。
- 不能提升理解的图、代码、表格和公式应删除；视觉材料不能只是重复正文。

## 命令型技术指南

- 先说明对象是什么、解决什么问题、什么时候不应该使用，再进入协议和命令细节。
- 所有命令集中在一个主章节，例如“命令完整指南”；命令分组和具体命令使用下级标题。
- 核心命令统一说明：用途、适用时机、关键入参、成功出参、通知或反向请求、最小可运行示例、失败与版本边界。
- 核心调用链给完整 Demo；低频或实验命令使用紧凑表格和最小请求/响应，明确实验状态与校验版本。
- 完整命令附录可以很长，但正文必须先建立读者需要的运行模型和选择标准；不要把文章写成没有主线的 Schema 副本。

## 语言与个人声音

- 使用精确名词和有方向的动词；能用普通语言准确说明时，不用术语制造专业感。
- 避免“赋能、颠覆、强大、先进、优雅、底层逻辑”等没有可观察含义的抬高词。
- 避免连续使用“不是……而是……”、强行凑成三点、每节重复总结和过度整齐的段落节奏。
- 允许长短句交替；重要句不要埋在括号、从句和附带条件中。
- 保留作者愿意反复追问的主题：环境、状态、权限和证据由谁拥有，行动在哪里发生，失败后如何恢复和接管。
- 作者声音来自观察、取舍、证据偏好和承认不知道，不来自“专业、深刻、有洞察”等语气标签。

## 分轮修订

不要在一轮里同时修正所有问题：

1. **真**：检查事实、版本、引用、推断强度和不能公开的内容。
2. **理**：只读标题、中心句和每段首句，检查顺序、重复与章节必要性。
3. **人**：补足读者不知道的前提、关键跳跃、最强异议和读后去向。
4. **象**：确认抽象判断有场景、机制、代码、数据、反例或图示承载。
5. **气**：拆分失去重音的长句，调整段落速度，保留作者自己的判断节奏。
6. **省**：删除套话、自我表演、重复结论和因投入成本而舍不得删的资料。
7. **验**：运行内容检查、示例命令、链接与页面渲染验证；事实更新后同步 `lastmod`。

## 与 Agent 协作写作

- 开始前明确需要的是共写、教练、编辑还是批评；不要一边要求保留作者判断，一边让 Agent 重写立场。
- Agent 应先复述文章中心和最高杠杆缺陷，再修改正文。
- 不让 Agent 编造事实、案例、数据、引语、运行结果或作者感受。
- Agent 修改时保护中心判断和风险边界，不把所有文章改成平滑、统一的 Agent 文风。
- 大幅改变立场、经历或文章类型前必须明确说明；普通行文修订使用能够解决问题的最低强度。
- Agent 交付时区分“已修改”“本地验证”“已提交”“已推送”和“已部署”。

## 发布前质量门

- 能否用一句话复述全文中心，并说出一个会改变结论的条件？
- 目标读者是否能在开头知道为什么继续读？
- 每个主章节是否完成不可替代的动作，目录是否能复述全文主线？
- 事实、推断、判断和建议是否诚实区分？
- 每个关键关系是否被解释，而不只是被命名？
- 抽象判断是否有足够具体的机制、例子或证据？
- 是否认真处理了一个聪明反对者，而非设置稻草人？
- 图、代码和表格是否承担理解或证明功能？
- 结尾是否提供新的采用边界、行动或余味？
- 删除 20% 材料后中心是否更清楚；若是，继续删除。
- 修改后是否仍能辨认作者关注所有权、边界、证据和恢复的个人视角？
- Frontmatter、图片、链接、内容检查、明暗主题和移动端渲染是否通过？

## 最小写作检查单

如果时间有限，至少确认：

```text
一个明确读者
一个中心句
一种主导关系
一个能承载机制的例子或图
一个会改变结论的边界
一个不重复摘要的结尾
一次事实与版本检查
一次页面渲染检查
```
